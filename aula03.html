Dois níveis de privilégio

O processador tem um bit que define o que a instrução atual pode fazer. Isso é hardware, não convenção de software — não dá para burlar por código.

MODO USUÁRIOOnde vivem o seu terminal, o navegador e a sua futura API. Não acessam hardware nem a memória de outro processo.
MODO KERNELAcesso total: toda a memória, todos os discos, todas as instruções da CPU. Só o núcleo do sistema roda aqui.

É essa separação que faz um programa travado derrubar só a si mesmo. E é ela que, em dezembro, vai dizer "permissão negada" quando o seu serviço tentar gravar num arquivo que não é dele.

aluno@unopar:~$ syscall --explain

Chamada de sistema

É a porta oficial entre os dois modos. O único jeito legítimo de um programa pedir alguma coisa ao sistema.

  • 01O ls pede: "abra este diretório". Ainda em modo usuário.
  • 02Uma instrução especial troca para o modo kernel.
  • 03O kernel confere: existe? você tem permissão? ← a Aula 10 mora aqui
  • 04Ele lê o disco de verdade e devolve os dados.
  • 05Volta ao modo usuário. O ls só imprime na tela.

São poucas as syscalls que importam para nós: fork cria processo, exec troca o programa, open e read e write mexem em arquivos, kill envia sinal. Você vai reencontrar todas.

aluno@unopar:~$ strace ls

Vendo a fronteira

aluno@maquina:~$ sudo apt install strace -y aluno@maquina:~$ strace ls 2>&1 | tail -6 openat(AT_FDCWD, ".", O_RDONLY|O_DIRECTORY) = 3 getdents64(3, ...) = 168 close(3) = 0 write(1, "Documentos Downloads projeto\n", 31) = 31 exit_group(0) = ? # quantas syscalls um simples "ls" precisa? aluno@maquina:~$ strace -c ls 2>&1 | tail -3
Fixe esta linha

O write(1, ...) destacado acima. O número 1 é a saída padrão — o stdout. Em dezembro, quando o log do seu serviço aparecer no journalctl, será por causa exatamente dessa chamada. Guarde.

aluno@unopar:~$ man ssh

SSH — Secure Shell

É um shell remoto criptografado. Você digita na sua máquina; o comando executa na outra; a resposta volta pela rede.

SUA MÁQUINAO cliente ssh — um processo comum, em modo usuário, como qualquer outro.
REDETudo criptografado. Ninguém no caminho lê o que você digita, nem a resposta.
SERVIDORO sshd recebe, autentica e cria um bash só para você. Esse bash é filho dele.

Repare na consequência: o seu shell remoto é filho do sshd. Quando a conexão cai, o pai encerra a sessão — e leva os filhos junto. Isso vai importar muito na Aula 13.

Rode nos dois lugares e compare

uptime — quanto tempo cada máquina está ligada? A sua reinicia todo dia. O servidor, não.

whoami — você é a mesma pessoa, mas é o mesmo usuário?

pwd — o seu /home aqui não é o mesmo de lá. São dois mundos.

aluno01@servidor:~$ cat regras.md

Regras de convivência

É uma máquina compartilhada. O que você faz afeta a turma inteira.

  • 01Trabalhe dentro do seu /home. Não é sugestão de organização — é o único lugar que é seu.
  • 02Nada de processo pesado sem avisar. Um laço infinito seu trava o trabalho de trinta pessoas.
  • 03Não tente acessar o diretório de outro aluno. A permissão vai impedir — e a tentativa fica registrada no log.
  • 04Sempre exit ao terminar. Sessão aberta consome recurso e ocupa lugar.
  • 05Quebrou algo? Avise. Esconder problema em servidor compartilhado é o pior hábito que existe na profissão.
